# 노션 개발 문서 작성

## 대상 데이터베이스

- 데이터 소스: `collection://425c740d-6de7-80b9-b69c-000b2e56d823` (개발 문서)
- 속성: `이름`(제목), `도메인`(select, 예: 라이브), `개발 내용`(text), `날짜`(date), `작성자`(person)
- 새 페이지를 만들기 전에 데이터베이스를 fetch해서 속성 이름과 스키마를 확인한다. 옛 데이터 소스(`기록보드`, `collection://417c740d-6de7-80ab-ac3a-000b2a089697`)는 쓰지 않는다.

## 1단계: 기능 종류 정하기

작업 내용을 보고 종류를 하나 고른다. 여러 종류가 섞이면 주된 종류로 고르고, 나머지는 "기능 요약"에 적는다.

| 종류 | 예 | 첨부 항목 |
|---|---|---|
| 도메인 모델 | 엔티티, VO, enum | 계층 구조 코드, 기능 요약, 질문·답변 |
| API | 엔드포인트 추가·변경 | 엔드포인트 표(메서드, 경로, 요청, 응답), 에러 코드, 예시 요청·응답 |
| 버그 수정 | 잘못된 동작 고치기 | 증상, 원인, 수정 내용, 재발 방지 테스트 |
| 설정·인프라 | 설정 파일, 배포, CI | 변경한 설정 항목 표, 적용 방법, 영향 범위 |
| 리팩터링 | 구조 변경, 이름 변경 | 변경 전후 구조, 바뀐 이유, 영향 범위 |

## 2단계: 공통 구성

모든 종류에 아래 두 항목을 맨 위에 둔다.

1. **이슈·PR 링크**: `이슈 : <link-preview ... source="...issues/N" />`, 이어서 `<p>pr </p>` 다음에 PR마다 `<link-preview ... source="...pull/N" />`
2. **토큰 사용 표**: 모델, 입력, 출력, 캐시 쓰기, 캐시 읽기, 합계. 한 줄은 PR 하나다.

## 3단계: 종류별 첨부 항목

- **도메인 모델**: 계층 구조를 코드 블록으로 그린다. 기능 요약은 엔티티마다 한 줄씩 쓰고 이름은 `<b>`로 감싼다. 질문·답변은 `### N. 주제` 헤더 아래 `<b>Q. ...</b>` 다음 `A. ...` 형식으로 쓴다.
- **API**: 엔드포인트 표, 에러 코드 표, 요청·응답 예시 코드 블록을 쓴다. 경로 규칙은 `docs/convention.md`를 따른다.
- **버그 수정**: 증상, 원인, 수정 내용, 재발 방지 테스트를 순서대로 쓴다. 원인이 확인되지 않았으면 "미확인"이라고 쓴다.
- **설정·인프라**: 바뀐 항목을 표로 쓴다. 항목, 이전 값, 새 값, 적용 방법을 적는다.
- **리팩터링**: 변경 전 구조와 변경 후 구조를 코드 블록으로 나란히 쓴다. 바뀐 이유와 영향 범위를 적는다.

## 작성 규칙

- 질문만 적지 않는다. 답변이 없는 질문은 "미정"이라고 쓰고, 무엇을 정해야 하는지 함께 쓴다.
- 확정된 내용만 답변으로 쓴다. 추측이면 추측이라고 표시한다.
- 기존 페이지를 고칠 때는 전체를 먼저 fetch하고, PR 링크와 토큰 표는 그대로 보존한다.
- `_`가 노션 마크다운에서 `\_`로 이스케이프되는 경우가 있으니 원문을 그대로 쓴다.

## 토큰 사용량 집계

세션 기록(`~/.claude/projects/<프로젝트>/<세션ID>.jsonl`)의 assistant 메시지에서 `message.usage`를 message id 기준으로 중복 없이 합산한다. 합계는 입력 + 출력 + 캐시 쓰기 + 캐시 읽기다. 집계 기준(시작 시점, 끝 시점, 무관한 대화 포함 여부)을 본문에 한 줄로 적는다.

## 관련 규칙

- PR 본문 템플릿과 커밋 규칙은 `docs/git-workflow.md`를 따른다.
- 노션은 외부에 공유되는 곳이므로, 사용자가 요청했을 때만 페이지를 만들거나 고친다.
